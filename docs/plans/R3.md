## 1. 機能要件と受け入れ基準

### F3-1. 高さ指定日照（「3階の日当たり」）

- 診断カードの日照セクションに**視点高さセレクタ**を追加。
  - **一般地点**（クリック地点・住所検索）: 1〜15階。**1階 = 地面+1.2m、以降 +3.0m/階**（k階 = base + 1.2 + 3.0×(k−1)）。
  - **建物クリック時**: 「屋上」＋「n階〜1階」。屋上 = `_zmax` + 1.2m。各階は `_zmin`〜`_zmax` を階数で内挿（§3.1.1）。
- セレクタ変更で**デバウンス400ms後に日照のみ再計算**。再計算中は旧結果を薄表示（stale）のまま進捗%を表示し、完了で差し替え。連続変更時は古い計算を**キャンセル**（結果破棄でなく計算ループ自体を停止）。再計算ではカメラ移動・プリロード待ちをしない。
- v1.0既知の制限「自建物に遮蔽される」を解消: 屋上選択で自建物の上から計算。各階選択時は自建物の扱いを §3.1.2 の方式で処理。
- **受け入れ基準**:
  1. e2e: 中野駅前の建物クリック→「1階」と「屋上」の冬至日照時間に**有意差**（屋上 ≥ 1階、かつ差 ≥ P0で実測確定する閾値。暫定: 差 ≥ 0.5h または 屋上 ≥ 1階×1.2）。
  2. e2e: セレクタを素早く2回変更→最終選択の階数の結果のみが表示される（多重計算・古い結果の上書きが起きない）。
  3. 既存e2e 52項目が無改変でパス（既定表示は従来と同一: 地面+1.2m・3日付・93セル）。

### F3-2. 日影マップ（エリアの日照ヒートマップ）

- 左パネルに新セクション「日影マップ」。**画面中心200m四方・10mグリッド（21×21=441点）**の冬至（既定。春分/夏至も選択可）日照時間を計算し、地表に色分けオーバーレイ＋凡例を表示。
- **粗→精の段階化**: 40m（6×6）→ 20m（11×11）→ 10m（21×21）の入れ子グリッドで段階的に精細化（格子が入れ子なので総計算点数は441点のまま）。
- 計算は rAF 分割（1フレーム8ms予算）で実行し、**進捗バーと中断ボタン必須**。中断時は計算済みセルまでの部分結果を表示保持。計算中も地図操作・診断がブロックされない。
- **キャッシュ**: 同一条件（中心スナップ位置・範囲・ピッチ・日付・建物レイヤー種別）の再計算を回避（LRU 4件、§3.2.5）。ヒット時は即座に再描画。
- 建物レイヤー「非表示」時は「建物モデルを表示してください」を出して計算しない。
- **受け入れ基準**:
  1. 実機Chrome: 中野四季の森公園周辺で「ビル北側が濃い影・公園が明るい」分布が視認できるスクリーンショット（手動チェックリスト項目、リリース条件）。
  2. e2e（CI/SwiftShader）: 縮小グリッド（100m/20m=36点）で完走・凡例表示・オーバーレイ描画・中断・キャッシュヒットが動作。計算中の rAF 間隔中央値 < 250ms（実機基準は<50msで手動側）。
  3. e2e: 計算中に診断カード操作（閉じる）が即応する。

### F3-3. 精度改善

- **プリロードの置き換え**: `prepareTiles` のカメラテレポート方式を廃止し、`pickFromRayMostDetailed` による**太陽経路ウォームアップ**（§3.3.1）に置き換える。カメラが勝手に飛ばなくなる（UX改善を兼ねる）。SwiftShader/実機で不安定な場合のフォールバックとして現行方式（＋複数方向へのカメラ振り強化版）を機能検出付きで残す。
- **遠方高層ビル対策**: 日影マップに「高精度モード」オプション（既定OFF）: 計算中のみ `maximumScreenSpaceError` 16→8、終了時に復元。`totalMemoryUsageInBytes` を監視し閾値超過で自動無効化（§3.3.2）。
- **限界の明文化**: README に「日照・日影の前提と限界」節を追加、UI注記を更新。特に**中野区タイルセットのみ読み込むため区外（新宿・渋谷等）の高層ビルの影は考慮されない**こと（中野坂上・東中野など区境で影響）を新たに明記。地形起伏・樹木は引き続き未考慮。
- **受け入れ基準**:
  1. e2e: 住所検索診断の実行前後でカメラ位置が強制テレポートしない（flyTo の目的地以外へ飛ばない）。
  2. e2e: 置き換え後も既存の日照アサーション（raysCast>50、3日付、夏至≥冬至、エラーなし）がパス。
  3. README/UI注記の更新がされている（e2eで注記文言を確認）。

## 2. 技術設計

### 3.1 F3-1: 高さ指定日照

#### 3.1.1 階数→高さ変換の仕様

純粋関数として `js/sunlight.js` に追加（Cesium非依存にしてNode単体テスト対象にする）:

```
floorHeights(kind, params) の仕様
─ 一般地点 (kind='ground'):
    h(k) = base + 1.2 + 3.0 * (k - 1)     k = 1..15
─ 建物 (kind='building', _zmin/_zmax あり):
    F = Number(地上階数プロパティ) が 1..60 の整数ならそれ
        なければ max(1, round((zmax - zmin) / 3.0))
    perFloor = (zmax - zmin) / F                       ← _zmin/_zmax からの内挿
    h(k) = min(zmin + 1.2 + perFloor * (k - 1),  zmax - 0.3)   k = 1..F
    h(屋上) = zmax + 1.2
─ 建物だが _zmin/_zmax 欠損: 一般地点仕様へフォールバック（base = estimateBaseHeight）
```

建物属性名は既存 `buildingTableHtml` と同様に `地上階数` を第一候補、`storeysAboveGround` 系を予備とする（P0で駅前建物の実プロパティ名を確認して固定）。

#### 3.1.2 自建物の扱い（各階選択時）

各階のレイ原点は建物内部/外壁面になるため、そのままでは自建物の壁に即ヒットして0hになる。2案を用意し **P0スパイクで採用を決定**する:

- **主案: objectsToExclude で自建物フィーチャを除外**。`pickFromRay` の第2引数に `picked`（`Cesium3DTileFeature`）を渡して除外できるか P0 で検証（非公開APIのため実挙動確認が必須）。除外できれば「その階の全方位の空」を評価でき、意味が明快。
- **代替案: クリック面の外側オフセット**。除外が効かない場合、クリック時のワールド座標（外壁/屋上面上）から**カメラ方向（水平成分）へ1.5m**オフセットした位置を原点にする（クリックで見えている面＝カメラ側が屋外側であることを利用）。「クリックした面の側の日当たり」という意味付けになるため、採用時はUI注記に明記する。

どちらの場合も、屋上（zmax+1.2）は建物の上なので特別扱い不要。

#### 3.1.3 再計算のUX（デバウンス・キャンセル）

- `estimateSunlight` に `opts.isCancelled: () => boolean` を追加し、**スロットループ内で毎チャンク確認して中途離脱**する（現状は runToken で結果を捨てるだけで計算が走り切る。F3-2で1万本規模になるため、キャンセルは「計算停止」に格上げする。F3-1でも同じ機構を使う）。
- diagnose.js に `sunRunToken` を追加: セレクタ `change` → 400msデバウンス → `sunRunToken++`（旧計算の isCancelled が true になる）→ 新計算。実装は既存 runToken パターンの踏襲。
- 再計算時は `prepareTiles`/warm-up をスキップ（初回診断で読み込んだタイルは上方向にも有効。建物タイルは建物全体を含むため高さ変更で追加ロードは不要）。ただし初回warm-upが失敗していた場合のみ再warm-up。
- 表示: 旧タイムラインに `.stale` クラス（opacity 0.5）＋「再計算中… n%」。完了で差し替え。**`.sun-day` / `.sun-bar` / セル数93 のDOM構造は維持**（既存e2e互換）。セレクタは `.sun-head` の外側（セクション先頭）に置く。

#### 3.1.4 UI

日照セクション先頭に1行:
```
視点の高さ: [▼ 1階（+1.2m）]  … 一般地点: 1階〜15階
視点の高さ: [▼ 屋上（45.3m）] … 建物: 屋上 / n階 / … / 1階
```
現在の実高さ（m）をoption文言に併記。注記文言に「視点高さ ○○m（○階）」を追加。

### 3.2 F3-2: 日影マップ

新モジュール `js/shademap.js`（計算エンジン＋キャッシュ）と `main.js`/`index.html`/`style.css` へのUI追加。

#### 3.2.1 グリッド設計

- 範囲: 実行時の**画面中心**（`camera.pickEllipsoid(画面中央)`）を中心に200m四方。中心は10m格子にスナップ（キャッシュヒット率向上のため。基準原点は中野駅座標に固定したENU格子）。
- ピッチ: 10m（441点）。UIで20m（121点）も選択可（低速機向け）。
- セル座標: 中心のENUフレームでオフセット（±100m）を計算し、`dLat = m/111320`, `dLon = m/(111320·cos(lat))` で経緯度化。描画矩形（§3.2.4）と同じ式を使い、ズレを構造的に防ぐ。
- **地盤高**: 中心1点を既存 `estimateBaseHeight` で取得し全セルの既定値とする。加えて `sampleHeightMostDetailed` を64点ずつバッチ実行し、返った点は個別値を採用（中心値±20mにクランプ）。建物屋上に乗ったセル（個別値 > 中心値+4m）はそのまま屋上面の日照として計算し、凡例に「建物屋上のセルは屋上面での値」と注記。サンプリング失敗時は中心値で続行（graceful degradation）。
- 視点高さ: 地盤+1.2m固定（日影マップは地表の評価。階数指定はF3-1のスコープ）。

#### 3.2.2 計算量

- 冬至の太陽高度≥5°は約7:40〜16:00 → 31スロット中**約26スロットが実レイ**。
- 最大レイ数 = 441 × 26 ≒ **11.5千本**。粗パス40m=36点(0.9千本) → 20m差分85点(2.2千本) → 10m差分320点(8.3千本)。
- 1本あたりコストは環境依存が大きいため**P0で実測**（§5テスト計画）。仮に実機0.3〜1ms/本なら総計算3.5〜11.5秒、SwiftShaderでは5〜10倍を想定。40mパスの初期表示は実機1秒前後で出る計算。
- 最適化: 太陽方向ベクトル（ECEF）は**スロットごとに中心ENUで1回だけ計算して全セルで共有**する（200m範囲では太陽方向は事実上一定。セルごとに変わるのはレイ原点のみ）。三角関数と行列積を441分の1に削減。

#### 3.2.3 計算スケジューリング（rAF分割・進捗・中断）

```
async runShadeMap(opts):
  token = { cancelled: false }   // 中断ボタン / 再実行 / レイヤー切替で true
  warmUp()                        // §3.3.1: 四隅+中心5点 × 朝/南中/夕3方向 = 15本を
                                  // pickFromRayMostDetailed（タイムアウト15s、失敗しても続行）
  地盤高バッチ取得（64点×rAF分割）
  for level of [40m, 20m, 10m]:
    for cell of levelの未計算セル:      // 入れ子格子なので計算済みセルは再利用
      for slot of 高度≥5°のスロット:
        pickFromRay(...)              // 同期
      cell.hours 確定 → canvasに塗る
      if (performance.now() - frameStart > 8ms):
        onProgress(done/total); await rAF; if (token.cancelled) return partial
    レベル完了 → オーバーレイ差し替え（§3.2.4）
  キャッシュ格納 → 完了
```
- 1フレームの予算は「本数固定」ではなく**経過時間8ms**で区切る（SwiftShaderと実機の速度差を自動吸収）。
- 進捗バーは総レイ数ベース。中断ボタンは計算中のみ表示。部分結果はそのまま残し「中断（○%まで計算済み）」を表示。
- 診断（F3-1）と日影マップの同時実行は、日影マップ実行中に診断が始まったら日影マップを自動中断する（シンプルな排他）。

#### 3.2.4 描画方式の比較と推奨

| 方式 | 描画コスト | ちらつき | 実装量・更新性 | 判定 |
|---|---|---|---|---|
| (a) GroundPrimitive群（441インスタンスを1プリミティブにバッチ） | 生成が非同期で重い（数百ms〜）。頂点量大。クラシフィケーションで建物にも被せるか選択が必要（被せると屋上が塗られ日影図として不自然） | レベル切替時に作り直し→1〜2フレーム消える | 色更新は可能だがセル数変更（粗→精）で作り直し | 不採用 |
| **(b) canvas 1枚を SingleTileImageryProvider で貼る** | **最小**（地表タイルへのテクスチャ合成1枚分）。建物には被らず地面のみ＝日影図として正しい見え方 | レイヤー差し替えで発生しうるが、**新レイヤーadd→次フレームでold remove**の順にすれば実質ゼロ | canvasに塗るだけ。差し替えはレベル境界（3回）＋精細パス中は2秒間隔に制限 | **採用** |
| (c) Entity矩形群（441 RectangleGraphics） | エンティティ441個は生成・ピッキング・バッチ化で最重量 | 追加中ちらつき | 論外に重い | 不採用 |

(b)の実装詳細:
- canvas 512×512px（200mで約0.4m/px、10mセル≒26px。にじみなし）。セルはブロック塗り、アルファ0.65。
- `SingleTileImageryProvider`（1.130では `tileWidth`/`tileHeight` を明示するコンストラクタ形式で非推奨警告を回避）に `canvas.toDataURL('image/png')` と `Cesium.Rectangle.fromDegrees(west, south, east, north)` を渡し、`viewer.imageryLayers.add`。
- 差し替え手順: 新レイヤー add → `postRender` 1回待ち → 旧レイヤー remove。背景切替（航空写真/淡色）とは独立に最上位に保つ。
- 色スケール（凡例と一致させる純関数 `hoursToColor(h, maxH)`）: 0h=濃紺紫 `#1e2a5a` → 2h `#5b4a9e` → 4h `#a86fae` → 6h `#e8a86a` → 最大 `#ffe08a`。凡例は5段＋「建物屋上セル」注記。

#### 3.2.5 キャッシュ

- キー: `date | pitch | sizeM | スナップ済み中心(10m格子ID) | 建物レイヤー種別(lod1/lod2/lod2notex) | 高精度モード有無`。
- 値: `Float32Array(441)` の時間値＋完了フラグ＋canvas再生成に必要なメタ。**完走した計算のみ**格納（中断分は格納しない）。
- LRU 4件、メモリのみ（sessionStorage永続化はしない）。建物レイヤー切替・ページ再読込で消えてよい。
- ヒット時: canvasを再描画してレイヤーを貼るだけ（<100ms）。「キャッシュから表示（計算日時）」を小さく表示。

### 3.3 F3-3: 精度改善

#### 3.3.1 プリロードの置き換え: 太陽経路ウォームアップ

現行 `prepareTiles`（カメラテレポート＋allTilesLoaded待ち）を次で置換:

```
async warmUpSunPath(scene, origin):
  機能検出: typeof scene.pickFromRayMostDetailed === 'function' かつ P0で動作確認済みフラグ
  対象方向: 冬至・春分・夏至の 8,10,12,14,16時のうち高度≥5°の方向（重複を方位10°粒度で間引き、
            計8〜12本）
  Promise.allSettled で並列発射、全体タイムアウト15秒
  → MOST_DETAILED_PICK パスがレイ経路上の最詳細タイルを画面と無関係にロードするため、
    以後の同期 pickFromRay がロード済みタイルに当たる
```

- **カメラを動かさない**ため、住所検索時は flyTo の見た目のまま診断が進む（現状の「診断のたびに上空400mへテレポート」が消える）。`camera.moveEnd` を最大2.5秒待ってから開始する（描画負荷の競合回避）。
- フォールバック（機能検出失敗 or P0でSwiftShader不安定と判明した場合）: 現行 `prepareTiles` を維持しつつ、`camera.setView` を**東西南北4方位×pitch −30°**に振って各600ms待つ強化版を `prepareTilesMulti` として追加。どちらを使ったかは結果オブジェクトに記録し注記に反映。
- 日影マップのウォームアップは §3.2.3 の15本（範囲が広いので点を散らす方を優先）。
- warm-upでロードしたタイルが計算中に追い出されないよう、計算中のみ `tileset.cacheBytes` を既定(512MB)→768MBへ引き上げ、終了時復元（公開API。LOD2テクスチャ付きで効果大）。

#### 3.3.2 maximumScreenSpaceError 一時変更の評価と限定採用

- 効果: msse 16→8 で遠方タイルが細かいLODで読まれ、遠方高層ビルの遮蔽判定が改善。
- 副作用（採用を限定する理由）:
  1. **メモリ**: LOD2テクスチャ付きでは使用量が急増し、`cacheBytes`(512MB) 超過時のアンロード/再ロードの顫動が起きる。モバイルではクラッシュリスク。
  2. **再ロード**: 復元時に全タイルの選択が変わり、画面がちらつく＋ネットワーク再取得が走る。
  3. 計算時間: タイル数増で warm-up が伸びる。
- 採用方針: **日影マップの「高精度（建物を細かく読み込む）」チェックボックス（既定OFF）のみ**に載せる。ON時は計算開始時 16→8、終了/中断時に必ず復元（try/finally）。`totalMemoryUsageInBytes` を計算中2秒ごとに監視し、**1GB超で自動的にOFFへ戻して警告表示**。LOD2（テクスチャ付き）選択時はツールチップで「テクスチャなしLOD2/LOD1での使用を推奨」と注記。F3-1（点計算）には載せない（warm-upで十分＋診断のたびの再ロードはUX害が大きい）。
- P0でmsse=8時の `totalMemoryUsageInBytes` と再ロード挙動を実測し、閾値を確定する。

#### 3.3.3 限界の明文化（README・UI注記）

README「日照・日影の前提と限界」節＋UI注記に以下を明記:
- 地形起伏は未考慮（楕円体扱い。神田川の谷〜台地の高低差約20mは地盤高で近似するのみ）
- 樹木・フェンス・電柱等は未考慮
- **中野区の3D都市モデルのみを読み込むため、区外（新宿・渋谷等）の建物の影は考慮されない**（中野坂上・東中野など区境で過大評価の可能性）— 今回新規に明文化
- warm-upで軽減するが、未読込タイルによる見落としがゼロになる保証はない
- 本結果は参考情報であり、建築基準法の日影規制の検討や重要事項説明には使用できない

### (3) `pickFromRay` の `objectsToExclude` に `Cesium3DTileFeature` を渡した除外

**結論となる事実: フィーチャ単位の除外が効く。タイルセット全体は巻き込まれない。**

カメラ→建物 のレイ（`camera.getPickRay`）での基本挙動:

| ケース | 交差 | 返った object |
|---|---|---|
| 建物Aへのレイ / 除外なし | あり | **A 自身** |
| 建物Aへのレイ / `[featureA]` を除外 | あり | **A 以外の別フィーチャ**（A は返らない） |
| 建物Aへのレイ / `[featureA.primitive]`(=tileset) を除外 | あり | `undefined`（地球楕円体にヒット。建物は全て除外される） |
| 建物Bへのレイ / 除外なし | あり | **B 自身** |
| 建物Bへのレイ / `[featureA]` を除外 | あり | **B 自身のまま**（A除外が他建物に波及しない） |
| 建物Bへのレイ / `[featureA.primitive]` を除外 | あり | `undefined`（タイルセット全体が消える） |

実運用シナリオ（建物A: `_zmin`=37.36 / `_zmax`=137.95 / `bldg:storeysAboveGround`=22 / 3階相当 = 44.6m、太陽方向87本）:

| レイ原点 | 除外 | lit（遮蔽なしのスロット数 / 87） | 自建物Aにヒット | 他建物にヒット |
|---|---|---|---|---|
| クリック面上 44.6m | なし | 32 | 30 | 25 |
| クリック面上 44.6m | `[featureA]` | **61** | 0 | 26 |
| クリック面上 44.6m | `[featureA.primitive]` | 87 | 0 | 0 |
| 内部2m 44.6m | なし | 31 | 33 | 23 |

## P1実装記録（2026-07-31 / 実装: Claude (Opus) / コミット a88febc）

全テストパス（単体457項目〔新規 sunfloor.test.mjs 96〕・既存e2e 92無改変・新規 e2e-r3 24・e2e-r1 123・smoke 17）。既定挙動不変の実証: SwiftShader実測が v1.0 実測（冬至7.0h/春分8.7h/夏至10.0h）と完全一致。

### 計画からの逸脱（実装で確定した差分）

1. `warmUpSunPath(scene, origin)` の origin は `{lon, lat, height}` オブジェクト（太陽方向算出に経緯度が必要なため）。
2. warm-upの並列度は4（バッチごと `Promise.allSettled`、バッチ境界で isCancelled 確認）。全12本同時発射だと連続クリック時に多重warm-upが積み上がるため。実測4.1秒/12本。
3. `runSunlight` の順序変更: `estimateBaseHeight` を先読みの前に移動（warm-upのレイ原点に地面高さが必要）。日照結果は不変。
4. 建物クリック（fly=false）でも warm-up を実行する（従来は先読み自体をスキップ）。warm-up非対応時はカメラを動かせないため `prepareTiles` にフォールバックせず `method:'none'` を記録し注記を出す。
5. isCancelled は diagnose に配線済み（放置された計算ループが実停止する）。P2のデバウンス再計算の前提。
6. カメラ停止待ちは `moveEnd` に位置ポーリング（200ms×2回不変で早期解決）を併用。静止時は約0.5秒で開始。
7. e2eのカメラ位置サンプル閾値は >20 → ≥10 に緩和（SwiftShaderでは同期レイループ中に setInterval が実効2秒間隔まで間引かれるため。テレポート検出には粗い間隔で十分）。
8. レイ単価の評価には `msPerRayMedian`（実測7.3ms/本）を使うこと。`msPerRayMean`（32.9ms）は初回タイルロードに引きずられる。

- `floorHeights` の戻り値 `floors` はセレクタ表示順そのまま（一般=1階→15階昇順、建物=屋上→F階→…→1階降順）。要素は `{key, label, floor, height, isRoof}`。`estimated===true` で「階数は高さからの推定」注記、`fallback===true` は屋上選択肢なし。
- 再計算は `estimateSunlight(..., {originHeight, excludeFeatures: [picked], isCancelled})`。**`picked.primitive` を渡すとタイルセット全体が除外されるので必ずフィーチャのみ**。
- キャンセル時は `result.cancelled === true` で `days` は完成分のみ。diagnose は cancelled で早期return（P2の再計算パスも同じ扱いにする）。
- `sunRunToken` は isCancelled クロージャに条件を足すだけでよい（`() => !alive() || myToken !== sunRunToken`）。
- 注記文字列の末尾に先読みフォールバック文が入ることがある。文言追加時は「簡易計算」を含む既存文の順序を壊さない。
- e2eで建物クリックが必要な場合は `window.__nakano.viewer.scene.pick` で拾い `diagnosis.diagnose({picked})` を呼ぶ（canvasマウス操作禁止）。

- SwiftShaderは同期レイループ中にタイマーが飢餓状態になる（setInterval 200ms → 実効2秒）。rAF間隔の計測系アサーションはCI緩和値400msでも余裕が小さい。

### 設計確定の追補（P1.1で確定した仕様変更）

- **縮退建物ルール**: `zmax − zmin < 1.0m` は不正な包絡とみなし一般地点仕様へフォールバック（`fallback:true`）。従来の `max(zmin, …)` 下限ガードは削除。
- **推定階数の上限**: プロパティ欠落時の推定にも `BUILDING_FLOOR_MAX`(60) クランプを適用（両経路の値域を統一）。
- **floorHeights の入力**: `null`/空文字等は厳格パーサーで拒否（`Number(null)→0` 混入の禁止）。
- **cacheBytes ブースト区間**: 「計算中のみ」→「**先読み（warm-up）開始〜日照計算完了**」に拡大（設計確定#7の改訂）。`boostTilesetCache` は参照カウント方式で入れ子可。別タイルセットには no-op。
- **warm-up 0本は成功扱いしない**: `rays===0` は `method:'none'` + `fallbackReason` 記録で注記対象。
- `warmUpSunPath` は `opts.excludeFeatures` を受け `pickFromRayMostDetailed` 第2引数へ配線済み（P2はwarm-upにも自建物除外を渡せる）。
- キャンセルは `cancelSignal()` でPromise化できる（ポーリング100ms）。長い await はこれと race すること（P3必読）。
