# R4+R6 実装計画 (v2.0): マルチエリア展開と継続運用

作成: 2026-07-27 / 計画: Claude (Fable) / 実装: Claude (Opus)
ステータス: 計画（R1完了後に着手推奨）

## 0. 前提

v1.0（3Dビューア + 街カルテ）および R1（共有URL `#v=1&spot=…&cam=…&ov=…`、比較、用途地域オーバーレイ、ci.yml）の完了を前提に、ROADMAP.md R4 の3機能（データセット動的解決・エリア選択UI・品質担保）と R6（継続運用のCI/定期ジョブ）を実装する。

現行アーキテクチャの起点:
- `js/config.js` … 中野区(13114)のタイルURLがハードコード（`TILESETS` 7本・`ZONING_TILES` 3本・`PRESETS` 6視点）。`HAZARD_TILES`/`GEOCODE_URL` は元々全国対応
- `js/main.js` … `TILESETS`/`PRESETS` を直接import。fld2河川・tran・wtrのチェックボックスは `index.html` に静的定義
- `js/zoning.js` … `ZONING_TILES` を直接import（R1後はオーバーレイともタイルキャッシュ共用）
- `js/diagnose.js` … 洪水・土砂・都市計画・日照のオーケストレータ。洪水/土砂/住所検索は全国タイルなので**エリア非依存で既に動く**
- `js/sunlight.js` … 基準高フォールバックが35m（中野の実測値）にハードコード → R4で自治体別に要修正
- R1の `AREA_RECT`（中野区矩形）と `share.js` のハッシュスキーマを拡張する

設計原則の維持: ビルドレス静的サイト / データは実行時取得（**例外: 自治体→URL対応表JSONの同梱。実測に基づく判断、§1.4）/ APIキー不要 / 日本語UI。

**工数: L（Opus 2セッション想定）/ 依存: R1 / リスク: 中**

## 1. データソース実測（2026-07-27実測）

### 1.1 PLATEAUカタログAPI（REST全件）

`GET https://api.plateauview.mlit.go.jp/datacatalog/plateau-datasets`

| 項目 | 実測値 |
|---|---|
| HTTP | 200（**HEADは404＝非対応**。監視はGETで行うこと） |
| サイズ | **生 9,108,706 B（約8.7MiB）/ gzip転送 592,018 B（約578KiB）**、取得2.5秒 |
| CORS | `access-control-allow-origin: *`（`Origin: https://y-kanekoo.github.io` で確認） |
| キャッシュ | `cache-control: no-cache, must-revalidate` + 弱ETag。`If-None-Match` → **304**（1.1秒） |
| 内容 | datasets 7,763件。bldg 3D Tilesは1,065件・**448自治体コード**（市287 + 政令市の区161）。⚠️ `lod` フィールドは**文字列**（`"1"`）なので `Number()` 必須 |

**→ ブラウザ直読み案（ROADMAP F4-1の第1案）は棄却**。gzip転送578KBは許容範囲だが、生9.1MBのJSONパースが毎起動で発生し、「localStorageに7日キャッシュ」は**一般的な5MBクォータに物理的に入らない**。

### 1.2 GraphQL API（自治体単位クエリ）

`POST https://api.plateauview.mlit.go.jp/datacatalog/graphql`（⚠️ `/graphql` は404。`/datacatalog/graphql` が正）

| クエリ | 実測値 |
|---|---|
| `area(code:"13113"){ ...datasets }` | 渋谷区28データセット = **生14,129B / gzip 3,082B / 0.81秒** |
| 同 22206（三島市） | 15データセット = gzip 1,591B / 0.46秒 |
| `areas(input:{areaTypes:[CITY],datasetTypes:["bldg"]})` | 全国287市 = gzip 3,200B / 0.9秒 |
| CORS | `*`。preflight（OPTIONS+content-type）204で通過。introspection有効 |
| 便利な点 | `items` に `lod`(Int)・`texture`(enum)・fld項目名「計画規模」(l1)/「想定最大規模」(l2) が構造化されて入る。shelter/park/station等のGeoJSON/CZMLも取れる（R2で有用） |
| 制約 | 政令市の区は `__typename: Ward` で、区コード指定では**bldgのみ**返る（市レベルのfld/urfは親コードに紐づく）→ 区コード指定時は親市コードも併せて問い合わせる必要がある |

### 1.3 対応表JSONを実際に生成した実測

カタログ全件から `{citycode: {b1,b2,b2n,fld[],urf{},tran,wtr,year}}` をNodeで生成した結果:

| 版 | 内容 | 生 | gzip |
|---|---|---|---|
| フル | 全urfレイヤー・URL完全形 | 975,347 B | 146,036 B |
| **絞り込み版（採用）** | urfは UseDistrict/FirePreventionDistrict/HeightControlDistrict の3種のみ・fldは同一河川のl1/l2で**l2（想定最大規模）優先**に重複排除・共通URLプレフィックス除去 | **460,838 B** | **102,409 B** |

- 収録: 448自治体。データ欠損の内訳: **fld無し 187/448、UseDistrict無し 200/448、建物LOD1のみ 147/448** → F4-3の欠損UIは必須
- GitHub Pagesは静的JSONをgzip自動圧縮配信するため、実転送は約100KB

### 1.4 方式判断: **B案（月次生成した対応表JSONの同梱）を採用**

| 案 | 判定 | 理由（実測に基づく） |
|---|---|---|
| A. RESTカタログをブラウザ直読み | ✗ | 9.1MBパース/起動、localStorage不可（§1.1） |
| **B. GitHub Actionsで月次生成した対応表を同梱** | **◎ 採用** | 同一オリジン約100KB・起動経路に外部API依存を増やさない・**e2eで中継不要＝テストが決定的**・月次再生成のdiffがR6「データ年度更新検知」を恒久解決 |
| C. GraphQLで自治体単位に実行時解決 | △ 補完のみ | 最軽量（3KB）だが試験提供APIへの実行時依存が増える・curl中継ハーネスのPOST対応拡張が必要 |

C案は「対応表に無いcitycodeが指定された場合のランタイムフォールバック」として**P5のオプション**に残す（実装しなくてもR4は完結）。対応表の**生成元はREST全件**とする（1リクエストで済み、月1回なのでサイズは問題にならない）。

## 2. 機能要件と受け入れ基準

### F4-1. データセットの動的解決（config 2層化）

**仕様**
- 起動時にcitycodeを決定: 優先順 = URLハッシュ `city` > クエリ `?city=` > 既定 `13114`。5桁数字以外・対応表に無いコードは既定にフォールバックし「未対応のエリア指定です」トースト
- `data/area-index.json`（同梱・月次生成）を同一オリジンfetchし、`js/area.js` の `resolveArea()` が現行 `TILESETS`/`ZONING_TILES` と同形の **AreaConfig** を組み立てる
- 中野区は対応表fetch失敗時でも `config.js` の静的定数から組み立てて必ず動く（オフライン耐性・回帰安全網）
- fld項目は「想定最大規模」のみ採用（現行仕様と同じ）

**受け入れ基準**
- 単体: `resolveArea('13114')` の全URLが現行 `config.js` の値と**完全一致**（移行の等価性をテストで固定）。未知コード・欠損フィールドの異常系
- e2e: パラメータ無し起動で従来と同一挙動（既存e2e/smoke全項目が無修正でパス）

### F4-2. エリア選択UIと共有URL統合

**仕様**
- 左パネル最上部に「エリア: 中野区 ▼」。都道府県→自治体の2段 `<select>`（対応表から生成、448件）
- 切替は `location.hash` に `city` を書いてから **`location.reload()`**（タイルセット破棄・レイヤーUI再構築・R1オーバーレイ矩形差し替えを一括でやり直せる最も安全な方式。比較リストはsessionStorageなのでリロード後も残る）
- ハッシュスキーマはv=1のまま `city` キーを追加（省略時13114）。`?city=` で入ってきた場合はハッシュに正規化。比較スナップショットにもcityを持たせ、「地図で表示」でエリアが違えば切替してから診断
- スポットプリセット: `data/spots.json` に自治体別定義（13114=現行6視点を移設、13113/22206は本計画の地点から作成）。**未定義自治体のフォールバック**: ①「{自治体名}役所」をGSI住所検索で解決（`addressCode`一致を検証）→「役所」ボタン ②bldg tileset.json の root region 中心から「全体」俯瞰ボタン。検索プレースホルダも「{自治体名}○○」に動的化

**受け入れ基準**
- e2e: `?city=13113` で渋谷の建物が表示され、ハチ公前クリック診断で「0.5〜3.0m・商業地域」が出る。共有URL（`#v=1&city=13113&spot=…`）を新規ページで開くと渋谷にflyTo+診断復元
- e2e: セレクタで中野区→渋谷区に切替→URLと表示が渋谷に変わる

### F4-3. 品質担保（データ欠損UI）

**仕様**
- レイヤーパネルのfld/tran/wtrチェックボックスを**AreaConfigから動的生成**（fldは河川数ぶん。三島は狩野川水系、中野は2、渋谷は4）。無いものは「このエリアでは提供されていません」のdisabled表示
- LODラジオも動的化: LOD2が無い147自治体ではLOD1を選択状態にしLOD2をdisabled
- 診断カード都市計画セクション: UseDistrict等が無い自治体では「このエリアでは都市計画データが提供されていません」（洪水・土砂・住所検索・日照は全国動作なので従来通り）
- 日照の基準高フォールバック: 35m固定 → `AreaConfig.groundHeight`（tileset regionのminHeight）に変更
- タイトル文言は「中野区3Dビューア」→「3D街カルテ — {自治体名}」に動的化（**リポジトリ改名はユーザー判断事項のため本計画ではやらない**）

**受け入れ基準**
- e2e: `?city=22206`（三島）でLOD2ラジオがdisabled・tran/wtrが「提供されていません」・防火/高度地区が「提供されていません」表示になり、一番町の診断（区域外・近隣商業80/200）と大場川沿い（0.5〜3.0m）が正しく出る

## 3. アーキテクチャ（config動的化の設計）

**2層構造**: `config.js` は「静的デフォルト層」として現行exportを**一切変更しない**（既存の単体テストが `ZONING_TILES` 等を直接importしているため）。その上に「動的リゾルバ層」`js/area.js` を新設し、アプリ実行時は AreaConfig だけを見る。

```
data/
  area-index.json      … 新規（生成物・コミット対象）: 448自治体の対応表（§1.3絞り込み版スキーマ）
  spots.json           … 新規（手書き）: 自治体別スポットプリセット（13114/13113/22206）
scripts/
  build-area-index.mjs … 新規: RESTカタログ→area-index.json 生成（lodのNumber()変換・
                          fld l2優先重複排除・urf 3種抽出・URLプレフィックス除去・政令市の区への親市データマージ）
js/
  config.js            … 変更最小: DEFAULT_CITY='13114' と AREA_INDEX_URL を追加。既存exportは不変
  area.js              … 新規: parseCityCode(location) / loadAreaIndex() / resolveArea(index, code) => AreaConfig
                          / buildNakanoFallback()（config.js静的値から組立）/ areaRect(tilesetJson)
  main.js              … 変更: 起動をasync化（citycode決定→対応表→AreaConfig→viewer初期化→動的レイヤーUI生成）
  zoning.js            … 変更: queryZoning(lon, lat, tiles = ZONING_TILES) — 引数化のみ。tiles.use等がnullなら
                          {unavailable:true} を返す。404時は z16→15→14 の順で再試行（tilejsonでminzoom10確認済み）
  diagnose.js          … 変更: initDiagnosis(ctx) に areaConfig を追加、renderZoningの「未提供」分岐
  sunlight.js          … 変更: 基準高最終フォールバックを引数化（35m固定を廃止）
  share.js (R1)        … 変更: cityキーのserialize/parse追加（5桁数字バリデーション）
index.html / style.css … エリアセレクタDOM、レイヤーパネルのコンテナ化（動的生成に）
```

**AreaConfig 形**（現行構造の写像。呼び出し側の書き換えを最小にする）:

```js
{
  code: '13113', name: '渋谷区', pref: '東京都', year: 2025,
  tilesets: { bldgLod1, bldgLod2, bldgLod2NoTex,      // 無ければnull
              fld: [{ label: '荒川水系神田川流域', url }, ...], tranLod3, wtrLod1 },
  zoning: { use: {url,z:16,label}, fire: null, height: null },  // ZONING_TILESと同形・欠損はnull
  presets: [...],          // spots.json or フォールバック（役所ジオコード+region俯瞰）
  rect: {west,south,east,north},  // bldg tileset.json root regionから（R1 AREA_RECTの置換）
  groundHeight: 51.4       // region minHeight（日照フォールバック）
}
```

依存方向: `main.js`/`diagnose.js` → `area.js` → `config.js`。逆流なし。`area.js` の resolve部は純粋関数としてNode単体テスト可能に。

## 5. リスクと対策

| リスク | 対策 |
|---|---|
| 対応表の鮮度（月次の間にURL変更・年度更新） | PLATEAUの年度更新は主に年1回。月次refresh + `expectations:check` で検知しPR/issue自動化（§7）。404時の診断はgraceful degradation |
| 古い年度・別仕様の自治体で建物属性名が違う（三島=2023/spec2系） | `HEIGHT_PROP_CANDIDATES` の候補探索が既にある。`_zmin`が無いLOD1では基準高がregion minHeightに落ちる設計。e2eの三島で実挙動を固定 |
| 448自治体分のセレクタUI肥大 | 都道府県→自治体の2段selectで1画面あたり最大数十件 |
| reload方式切替のUX（一瞬白画面） | 切替頻度は低く許容。in-place切替は再構築が複雑でバグ源になるため採らない |
| 政令市の区（161件）はfld/urfが親市コードに紐づく | **生成器側で解決**: 区エントリ生成時に親市のfld/urf/tran/wtrをマージして格納。ブラウザ側は無知でよい |
| 洪水タイルが未整備の地域で「区域外」と誤解される | 注記に「浸水想定が公表されていない河川は表示されません」を追記 |
| `lod`文字列問題の再発 | 生成器で `Number()` 正規化 + fixture単体テストで固定（本計画の実測で発見済み） |

## 7. R6 継続運用タスクの具体化

### 7.2 `npm run expectations:check`（P5で追加）

現行 `expectations` は実測値を「出力する」スクリプト。`--check` モードを追加し、コード内に固定した期待値（§1.5の5地点+中野6地点）と実タイルの照合結果を**exit codeで返す**。カタログ照合（`resolveArea` の全URLに `curl GET -r 0-0`。**HEADは404なので使わない**）も含める。

### 7.3 `.github/workflows/refresh-data.yml`（新規）の仕様

```yaml
name: Refresh area index (monthly)

on:
  schedule:
    - cron: '0 21 1 * *'   # 毎月1日 06:00 JST
  workflow_dispatch:

permissions:
  contents: write
  pull-requests: write
  issues: write

jobs:
  refresh:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - run: npm ci
      # 1) カタログから対応表を再生成（448件未満/前回比2割減なら異常としてfail）
      - run: node scripts/build-area-index.mjs --out data/area-index.json --sanity-min 400
      # 2) 実タイル期待値の照合（中野6+渋谷3+三島2地点）
      - run: npm run expectations:check
      # 3) 差分があればPR作成（無ければ何もせず緑終了）
      - uses: peter-evans/create-pull-request@v6
        with:
          add-paths: data/area-index.json
          branch: bot/refresh-area-index
          commit-message: '対応表を再生成 (月次自動更新)'
          title: '【自動】PLATEAU対応表の月次更新'
          body: 'カタログAPIの差分を反映。expectations:check はパス済み。'
      # 4) 失敗時はissue起票
      - if: failure()
        uses: actions/github-script@v7
        with:
          script: |
            await github.rest.issues.create({
              owner: context.repo.owner, repo: context.repo.repo,
              title: `月次データ更新が失敗 (${new Date().toISOString().slice(0,10)})`,
              body: `run: ${context.serverUrl}/${context.repo.owner}/${context.repo.repo}/actions/runs/${context.runId}`,
            });

  e2e:
    runs-on: ubuntu-latest
    needs: refresh
    continue-on-error: true    # e2eの不安定さでPR作成を止めない
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - run: npm ci
      - run: npx playwright install --with-deps chromium
      - run: python3 -m http.server 8123 &
      # GitHub Actionsランナーは外部に直接出られるため中継不要（R1で追加したHARNESS_DIRECT）
      - run: HARNESS_DIRECT=1 npm run test:e2e
      - if: failure()
        uses: actions/github-script@v7
        with:
          script: |
            await github.rest.issues.create({
              owner: context.repo.owner, repo: context.repo.repo,
              title: '月次e2eが失敗（外部データ変化の可能性）',
              body: `run: ${context.serverUrl}/${context.repo.owner}/${context.repo.repo}/actions/runs/${context.runId}`,
            });
      - if: always()
        uses: actions/upload-artifact@v4
        with: { name: e2e-output, path: test/output/*.png }
```

補足仕様:
- `ci.yml`（R1）は変更不要
- relay-cacheはランナーでは使わない（`HARNESS_DIRECT=1`）
- 週次のネットワーク付き単体（R1 ci.ymlのschedule）はそのまま。役割分担: 週次=タイル値のドリフト検知、月次=カタログURL/年度のドリフト検知+反映
