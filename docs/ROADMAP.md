# ロードマップ: 中野区3Dビューア + 街カルテ

作成: 2026-07-27 / 計画: Claude (Fable)

v1.0（3Dビューア + 街カルテ地点診断）完成時点からの拡張計画。5つのリリース（R1〜R5）と継続運用（R6）で構成する。各リリースは独立して価値を出せる単位であり、順序の入れ替え・取捨選択が可能。

## 進め方（全リリース共通）

1. リリース着手時にFableが `docs/PLAN.md` 方式の詳細実装計画を作成（データソースの事前検証・実測期待値の確定を含む）
2. Opusエージェントがフェーズ分割で実装（フェーズごとにテストを通してからコミット）
3. 独立検証（単体＋e2e再実行・スクリーンショット確認）を経てpush

設計原則の維持: ビルドレス静的サイト / データは実行時取得 / APIキー不要（**R5のみ例外、要判断**）/ UIは日本語。

工数の目安は「Opus実装セッション」単位: **S**=半セッション、**M**=1セッション、**L**=2セッション以上。

## R1 (v1.1) 共有・比較・見える化 — 使ってもらうための土台

**ねらい**: 診断結果が「その場で消える」現状を改め、URLで共有でき、地点同士を比べられるようにする。用途地域を面で見せて「調べるツール」から「眺めて発見するツール」へ。

**工数: M / 依存: なし / リスク: 低**

### F1-1. 共有URL（診断結果のパーマリンク）
- 診断実行時にURLハッシュを `#spot=139.6739,35.6915&addr=弥生町二丁目` 形式で更新。ページ読込時にハッシュがあれば同地点へflyTo＋自動診断。
- カードに「リンクをコピー」ボタン。カメラ状態（heading/pitch/height）もハッシュに含め、見ていた画角まで再現する。
- **受け入れ基準**: 診断→URLコピー→新規タブで開くと同じカードが再現される（e2eで検証）。

### F1-2. 地点比較（最大3地点）
- カードに「比較に追加」ボタン。2〜3地点たまると比較テーブル表示に切替（行=診断項目、列=地点）。
- 比較対象は `sessionStorage` に保持（ページ再読込では消える割り切り。永続化はしない）。
- 比較テーブルからも共有URL発行（`#compare=lon1,lat1|lon2,lat2`）。
- **受け入れ基準**: 弥生町 vs 鷺宮の比較で浸水ランク・用途地域・日照の差が1画面で見えること。

### F1-3. 用途地域カラーオーバーレイ
- 既に点判定で使っているUseDistrict MVTを、面としても3D地図に重ねる（用途地域ごとの慣用色で半透明表示、凡例付き）。
- 技術方式: **自前のMVT→canvasタイル描画ImageryProvider**を実装（`Cesium.ImageryProvider` インターフェース準拠、`requestImage` でMVTを取得→2D canvasにポリゴン描画して返す）。外部ライブラリ追加なし（既存のpbf/vector-tile CDNを流用）。z=14〜16の配信範囲を確認済み。
- 同方式で防火地域・高度地区もトグル追加（初期OFF）。
- **受け入れ基準**: オーバーレイONで駅前が商業系色・周辺が住居系色に塗り分けられ、凡例と一致。FPSが体感で劣化しない（タイルキャッシュ実装）。

### F1-4. 小さなUX改善（まとめて）
- 検索候補の矢印キー選択・Enter確定 / 診断カードのセクション折りたたみ / 「診断した地点の履歴」ドロップダウン（直近5件、sessionStorage）/ 検索ボックスに位置情報ボタン（Geolocation API、HTTPS前提でGitHub Pages上のみ動作）。

## R2 (v1.2) 防災強化 — 「街カルテ」の本丸を深くする

> **実装済み（2026-07-28）**。詳細な実測値・実装記録は `docs/plans/R2.md` を参照。
> F2-2（内水氾濫）は調査の結果「中野区は重ねるハザードマップに配信なし」と結論し、
> 注記＋公式リンクのみに縮小した（`01_naisui_data` は**プレフィックス誤り**で、
> 正しくは `02_naisui_data` / `02_naisui_pref_data/{都道府県コード}/`。中野区は両方とも404）。
> 計画時の実測で低コストと分かった「洪水（計画規模）判定」を F2-5 として追加実装した。

**ねらい**: 洪水の「深さ」に「時間」と「逃げ場所」を加え、防災ツールとしての実用度を上げる。

**工数: M / 依存: なし（R1と並行可） / リスク: 中（データ調査タスクあり）**

### F2-1. 浸水継続時間【配信確認済み】
- `01_flood_l2_keizoku_data` タイル（中野区分の配信をHTTP 200で確認済み・2026-07-27）を色判定し、「浸水が引くまでの目安時間（12時間未満/〜1日/〜3日/…）」をカードの洪水セクションに追加。
- 凡例色は実装時に実タイルから確定（v1.0のP2と同じ手順）。

### F2-2. 内水氾濫【調査完了・スコープアウト】
- 正しいパスは `02_naisui_data`（統合版）と `02_naisui_pref_data/{都道府県コード}/`。**中野区は両方とも404**で、掲載市町村一覧（`csv/naisui.csv`、62市町村）にも中野区はない（東京都は昭島市・福生市のみ）。PLATEAUカタログにも中野区の内水モデルはない。
- 代替（東京都下水道局の浸水予想区域図CSV）は神田川流域北側だけで27.3MBあり同梱の規模を超えるため不採用。
- 実装は注記＋中野区ハザードマップへのリンクのみ。将来配信が始まったら `HAZARD_TILES` に1エントリ追加するだけで対応できるよう、hazard.js は汎用のままにしてある。

### F2-5. 洪水浸水想定区域（計画規模）【追加実装】
- `01_flood_l1_shinsuishin_newlegend_data`（`newlegend` なしは中野区404）を色判定し、カードに「計画規模の想定」行を追加。新凡例は既存6色＋細分2色の8色構成なので、専用テーブル `FLOOD_LEGEND_L1` で判定する。

### F2-3. 避難所・避難場所レイヤーと「最寄り避難所」
- データ: 国土数値情報「避難施設データ（P20）」または中野区オープンデータの避難所CSV。**CORS配信が期待できないため、前処理してGeoJSON（数十KB）をリポジトリに同梱する**（データは実行時取得、の原則の初の例外。出典・取得日・ライセンスをファイル内に明記し、`npm run expectations` 同様の再生成スクリプトを用意）。
- 3D地図にピン表示トグル＋診断カードに「最寄りの避難所: ○○小学校 約450m」（直線距離。経路距離ではないことを注記)。
- **受け入れ基準**: 任意の診断で最寄り避難所名と距離が表示される。

### F2-4. 浸水深の3D表現
- 診断地点の浸水ランクに応じて、地点周辺（半径150m程度）に該当深さの半透明水面（`EllipseGraphics`、地表+深さ上限）を表示するトグル。「3mの浸水」が建物の何階に相当するかが直感的に見える演出。
- 既存の洪水3D Tilesレイヤー（PLATEAU fld）との使い分けをUI上で説明。

## R3 (v1.3) 日照・日影の本格化 — 差別化機能を磨く

> **実装済み（2026-07-31）**。詳細は `docs/plans/R3.md` を参照。
> P0実測で効果がなかったmsse高精度モードはR3のスコープから削除し、P3はエンジン＋単体テスト、ブラウザE2EはP4へ移した。
> E2E実績は既存 `e2e.test.mjs` 92項目を無改変で維持し、R3新規は高さ指定日照74項目＋日影マップ50項目の計124項目。

**ねらい**: v1.0の日照は「地上1.2m・簡易」。不動産検討の実用に近づける。

**工数: L / 依存: なし（ただしR1の共有URLがあると価値が上がる） / リスク: 中〜高（レイキャスト精度・性能）**

### F3-1. 高さ指定日照（「3階の日当たり」）
- 診断カードの日照セクションに階数セレクタ（1〜15階、1階=地面+1.2m、以降+3m/階）。変更で再計算。
- 建物クリック時は「この建物の屋上」「各階」を選べるようにする（`_zmin`〜`_zmax`を階数で内挿）。
- v1.0の既知の制限「建物クリックで自建物に遮蔽される」もこれで解消（屋上高+1.2mを選べばよい）。
- **受け入れ基準**: 駅前の建物で1階と屋上の冬至日照に有意差が出ること（e2e）。

### F3-2. 日影マップ（エリアの日照ヒートマップ)
- 指定範囲（初期値: 画面中心200m四方・10mグリッド=441点）について冬至の日照時間を計算し、地表に色分けオーバーレイ（`GroundPrimitive`または半透明矩形群）。
- 計算量対策: レイ数 = 441点 × 31時刻 ≒ 1.4万本。`requestAnimationFrame`で分割実行し進捗バー表示、中断ボタン必須。結果はグリッド解像度を落とした先読み→段階的精細化。
- **受け入れ基準**: 中野四季の森公園周辺で「ビル北側が濃い影・公園が明るい」分布が視認できるスクリーンショット。計算中もUI操作がブロックされない。
- **リスク**: SwiftShader（CI環境）では性能検証が困難。実機Chromeでの手動確認をリリース条件に含める。

### F3-3. 精度改善
- 診断前プリロードは、`pickFromRayMostDetailed`による太陽経路warm-upを採用。カメラを動かさずに画面外の建物タイルを先読みし、API非対応時だけ従来のカメラ移動方式へフォールバックする。
- P0実測で主方式の安定動作を確認できたため、カメラを多方向へ振る強化版は実装していない。
- `maximumScreenSpaceError`を下げる高精度モードは、中野区タイルセットで読込タイル・メモリ・選択LODの変化がなかったためR3のスコープから削除した。
- 限界の明文化: 地形起伏・樹木・区外建物は未考慮で、warm-up後も未読込タイルの見落としが残り得ることをREADMEとUI注記へ反映。

## R4 (v2.0) マルチエリア展開 — 「中野区」を設定値にする

> **実装済み（2026-07-31）**。詳細は `docs/plans/R4.md` を参照。
> 同梱の対応表は448自治体・実測1.2MB（gzip 126KB）となり、エリア切替は安全性を優先したreload方式で実装した。
> R5相当として計画に残したGraphQLランタイムフォールバックは未実装。

**ねらい**: ハードコードされた中野区のデータURLを月次生成の同梱対応表から解決し、URLパラメータで**全国448自治体コード**に展開する。

**工数: L / 依存: R1（共有URL基盤）推奨 / リスク: 中**

**実現性の裏付け（2026-07-27実測）**: PLATEAUカタログAPI（`api.plateauview.mlit.go.jp/datacatalog/plateau-datasets`）を集計した結果、建物3D Tilesを持つ**448自治体コード（市287 + 政令市の区161）**を確認した。ハザードタイル（重ねるハザードマップ）と住所検索は元々全国対応。

### F4-1. データセットの動的解決
- 起動時に `?city=13114`（省略時は中野区）を読み、月次生成して同梱する`data/area-index.json`から該当自治体の bldg/fld/tran/wtr/urf の配信URLを解決して`AreaConfig`を組み立てる。ブラウザ起動時に外部カタログAPIは呼ばない。
- 対応表は`contentHash`を持つ決定的出力とし、全448自治体の建物URLコードsanity、単体テスト、実タイル期待値照合を月次ワークフローで実行する。
- 中野区スポットプリセットは自治体別定義に分離し、未定義の自治体は住所検索APIの「役所」と建物tilesetの範囲から作る「全体」プリセットを生成する。

### F4-2. エリア選択UI
- 左パネル最上部に「エリア: 中野区 ▼」。都道府県→自治体の2段選択。切替でカメラ・タイルセット・診断がその自治体に切り替わる。
- 共有URLに`city`を含める（R1のハッシュ形式を拡張）。
- **受け入れ基準**: `?city=13113`（渋谷区）で渋谷の建物が表示され、渋谷駅前の診断（浸水・用途地域）が正しく動く（e2eは渋谷区と、LOD1のみの地方都市1つの計2エリアで実施）。

### F4-3. 品質担保
- 自治体によりデータの有無が異なる（fldが無い、urfが無い等）。「このエリアでは提供されていません」表示を全セクションに実装。
- リポジトリ名/タイトルの再考（nakano-3d → 汎用名）はこのタイミングで判断。

## R5 (v2.1) AIコンシェルジュ — 要判断（デフォルトでは見送り）

**ねらい**: 診断結果・比較結果をLLM（Claude API）で要約し、「小さい子がいる家庭なら…」のような観点別コメントを生成する。

**工数: M / 依存: R1（比較機能） / リスク: 高（アーキテクチャ原則に抵触）**

**判断が必要な理由**: APIキーが必要になり「完全静的・キー不要」の原則を破る。選択肢:

| 方式 | 内容 | 難点 |
|---|---|---|
| a. BYOK | ユーザーが自分のAPIキーをlocalStorageに保存しブラウザから直接呼ぶ | 一般ユーザーには使えない。CORSはAnthropic APIの`anthropic-dangerous-direct-browser-access`で回避可能 |
| b. プロキシ | Cloudflare Workers等の無料枠でキーを秘匿した中継を立てる | リポジトリ外のインフラ管理が発生。悪用対策（レート制限）必須 |
| c. 見送り | 事実表示に徹する現方針を維持 | — |

**推奨**: 当面 **c（見送り）**。R1〜R4の価値が十分大きく、キー管理の複雑さに見合わない。個人利用で試したくなったら a を実験的に `?ai=1` フラグで足すのが最小コスト。

## 商用化トラック（R7）とモバイル展開（R8）

> 2026-07-27追記。「商用で出せるか」「スマホ版を出せるか」の検討結果と、そのために必要な作業。

### 前提整理: 現状の構成は商用利用できるか → **原則できる。ただし2つの置き換えが必要**

各構成要素の利用条件（2026-07-27時点の各規約・ドキュメントに基づく。着手時に必ず原文を再確認すること）:

| 構成要素 | ライセンス/規約 | 商用利用 | 条件・注意 |
|---|---|---|---|
| PLATEAU 3D都市モデル（データ自体） | CC BY 4.0 / 政府標準利用規約準拠 | **可** | 出典表示（現在のUI表記で概ね充足。商用時は利用規約ページに正式記載） |
| **PLATEAU配信サービス**（assets.cms.plateau.reearth.io） | 試験的提供・**提供期間/サービスレベル無保証** | 利用自体は可 | **商用本番には不適**。突然の停止・URL変更があり得る → C2でセルフホスト化 |
| 地理院タイル（背景地図） | 国土地理院コンテンツ利用規約 | **可** | 出典明記。リアルタイム読込での背景利用は申請不要が原則。編集・加工時はその旨併記。一部成果は測量法の複製・使用承認が必要な場合あり（背景タイル利用では通常不要） |
| ハザードマップポータルのタイル | 政府標準利用規約準拠 | **可** | 出典明記。無保証。**災害時はアクセス集中で不安定になり得る**（防災商品なら要キャッシュ戦略） |
| **GSI住所検索API**（msearch.gsi.go.jp） | 明文化された公開API規約がない（試験公開扱い） | **グレー** | 商用・大量アクセスでの利用は避けるべき → C3で正式なジオコーダに置換 |
| CesiumJS | Apache-2.0 | 可 | ライセンス表記維持。Cesium ion（有料SaaS）は未使用なので課金なし |
| pbf / @mapbox/vector-tile | BSD-3-Clause | 可 | ライセンス表記維持 |
| 本リポジトリのコード | MIT | 可 | 商用クローズドソース化も可（MITのまま公開継続も可） |

法規上の注意（機能そのものより「見せ方」の問題）:
- **ハザード・日照の表示は「参考情報」であることの明示が必須**。特に宅建業法の重要事項説明（水害ハザードマップの説明義務）に代替利用されないよう、「本サービスは重要事項説明に使用できません。公式ハザードマップを確認してください」の明記。
- 不動産広告に組み込む場合は不動産表示の公正競争規約・景品表示法の観点でレビューが必要（有利誤認となる表現の禁止）。
- 「PLATEAU」ブランド・ロゴの使用はガイドラインに従う（データ出典表記と、サービス名への冠は別問題）。

### R7 商用化準備 — 依存の自立化と法務・運用整備

**工数: L / 依存: なし（ただしR4と同時期推奨） / リスク: 中**

#### C1. 法務・コンプライアンス
- 利用規約・免責事項・プライバシーポリシーページの作成（診断結果の非保証、重要事項説明への不使用、データ出典と取得日の明示）。
- 出典表記の正式化: フッター常時表示に加え、専用「データについて」ページに全データソース・年度・ライセンスを列挙。
- OSSライセンス一覧ページ（CesiumJS等のNOTICE集約）。

#### C2. データ配信の自立化（最重要）
- **PLATEAU 3D Tiles/MVTのセルフホスト**: G空間情報センターから中野区（展開後は対象自治体分）のオリジナルデータを取得し、自前のオブジェクトストレージ+CDN（Cloudflare R2/S3+CloudFront等）から配信。配信サービスの無保証リスクを排除する。
  - 目安コスト試算をプラン時に実施（中野区LOD2一式は数GB規模。R2なら egress無料で月額数百円〜）。
  - 年度更新の運用手順（ダウンロード→検証→差し替え）をスクリプト化。
- **ハザードタイルのキャッシュ層**: 直接disaportalを叩き続けるのではなく、エッジキャッシュ（Cloudflare Workers + Cache API等）を挟む。平常時のレイテンシ改善と災害時の可用性向上を兼ねる（キャッシュTTLは1日程度、出典・鮮度をUIに表示）。
- 静的ホスティングもGitHub Pagesから商用SLAのあるホスティング（Cloudflare Pages/Vercel等）へ移行。

#### C3. ジオコーダの正式化
- GSI住所検索APIを置換する。候補（プラン時に精度・料金・規約を比較検証）:
  1. **国土交通省 不動産情報ライブラリAPI**（無料・要APIキー・利用規約明確）
  2. Google Geocoding API（高精度・有料・Googleマップ以外への表示制約に注意）
  3. HERE / Mapbox Geocoding（有料・規約柔軟）
- APIキーが必要になるため、C2のエッジ層（Workers）にキーを秘匿した中継エンドポイントを実装（R5で検討した構成をここで先に作ることになる）。

#### C4. 計測・監視・品質
- プライバシーポリシーと整合するアクセス解析（Cloudflare Web Analytics等のクッキーレス計測を推奨）。
- 外部データソース死活監視（日次でtileset.json/タイルをHEADし、Slack/メール通知）— 既存の`npm run expectations`を監視ジョブ化。
- エラートラッキング（Sentry等）とパフォーマンス予算（初期表示3秒/モバイル）。
- 実機テストマトリクス（iOS Safari / Android Chrome / 低スペック端末）をリリース条件に追加。

#### C5. 収益化オプション（ビジネス判断・実装は選択制）
| モデル | 内容 | 実装コスト |
|---|---|---|
| B2B埋め込み | 不動産会社サイトへのiframe/SDK提供（物件座標を渡すと街カルテを表示） | M（R1の共有URLが土台） |

#### C6. リポジトリ・ブランド戦略
- 商用化時は **privateリポジトリへのfork（またはorganization移管）+ 現行公開リポジトリはOSS版として維持** を推奨。MITなのでクローズド派生は問題ない。OSS版を残すことは採用・広報上もプラス。
- サービス名・ドメイン取得、`nakano-3d`からの改名はR4（マルチエリア）と同時に。

### R8 モバイル展開 — PWAから始めてストア配信へ

**工数: R8a=S〜M, R8b=M / 依存: R8aはなし・即可 / リスク: 低〜中**

**結論: スマホ版は可能。リポジトリは分けない（同一リポジトリで出す）。**

#### R8a. PWA化（推奨・第一段階）— 同一リポジトリ・同一コード
- 現状でもモバイルブラウザで動作する（v1.0でモバイル幅のe2e済み）。これを「インストールできるアプリ」にする:
  - `manifest.json`（アイコン・スタンドアロン表示・テーマ色）+ Service Worker（アプリシェルとCDNライブラリのキャッシュ。地図タイルは鮮度優先でネットワークファースト）。
  - モバイル軽量モード: 初期LOD1・`maximumScreenSpaceError`引き上げ・タイルキャッシュ上限設定・`resolutionScale`調整。設定で「高画質(LOD2)」に切替可。
  - タッチUI調整: 診断カードをボトムシート化（スワイプで開閉）、日照計算などの重い処理に進捗と中断を必ず付ける。
  - 位置情報ボタン（R1-F1-4）で「いまいる場所を診断」が主要ユースケースになる。
- **受け入れ基準**: Lighthouse PWA監査パス。実機Android/iOSで「ホーム画面に追加」→スタンドアロン起動→診断完走。中間性能の実機でLOD1初期表示が5秒以内。
- 制約の明記: iOS SafariのWebGLメモリ制限が厳しいため、LOD2テクスチャは端末により不安定（軽量モードをデフォルトにする理由）。

#### R8b. ストア配信（第二段階・商用時）— Capacitorラッパー、モノレポ構成
- ネイティブ化はフルスクラッチせず **Capacitor**（WebViewラッパー）でWeb資産をそのまま包む。App Store / Google Play配信が可能になり、プッシュ通知（例: 大雨警報時に自宅地点のハザード再確認を促す）等のネイティブ機能も足せる。
- **リポジトリ構成: 分けずにモノレポ**。
  ```
  /            … Webアプリ本体（今のまま。PagesにもデプロイされるSSoT）
  /mobile/     … Capacitorプロジェクト（iOS/Androidシェル。Webビルドを取り込む）
  ```
  - 分けない理由: UI・診断ロジック・テストは100%共通で、分割すると二重メンテと乖離が必ず起きる。Capacitorシェルは薄い設定ディレクトリに過ぎない。
  - 分ける条件が生まれたら再検討: ネイティブ固有コードが肥大化した場合、モバイルのリリース周期をストア審査に合わせて完全分離したい場合、開発主体が別チームになった場合。
- ストア審査観点: 免責・出典ページ必須（C1が前提）、iOSは「Webサイトをただ包んだだけ」のリジェクト（ガイドライン4.2）を避けるため位置情報診断・プッシュ通知などアプリならではの機能を1つ以上入れる。
- **受け入れ基準**: TestFlight / 内部テストトラックでの実機動作、審査提出チェックリスト完備。

## 推奨実施順序と理由

```
趣味・ポートフォリオ路線:
R1 (共有・比較・用途地域面表示)   ← 最初。全後続の価値を底上げし、リスクが最も低い
 → R2 (防災強化)                ← データ調査を含むが独立性が高い
 → R3 (日照本格化)              ← 技術リスクが高いので基盤が安定してから
 → R4 (マルチエリア)            ← 最大の構造変更。機能が揃った状態で展開する方が効果的
 R5 は保留（判断事項）

商用を視野に入れる場合の差し込み:
R1 → R8a (PWA)                 ← 早期にスマホで使える形にして反応を見る（コスト小）
 → R2 → R7-C1 (法務ページ)      ← 公開範囲を広げる前に免責・出典を整備
 → R3/R4 → R7-C2/C3 (配信自立化・ジオコーダ置換) ← 本格商用の直前に
 → R8b (ストア配信)             ← C1完了が前提
```

- **R1が先**: 共有URLは「作ったものを人に見せる」ための最重要機能で、R2〜R4のすべての成果物の見せ方を改善する。実装も既存構造への追加が中心で安全。
- **R4を最後に**: config動的化は全モジュールに触る構造変更。機能追加が一段落してからの方が手戻りがない。
- 各リリースは約1〜2週間隔で1つずつ。まとめて実装せず、リリースごとにデプロイして使用感を確認してから次へ。
